CloudGuard Documentation

An agentic security & compliance auditor that continuously scans an AWS account, reasons about findings with Amazon Bedrock, scores severity, and remediates issues after explicit approval.

Phase 1 scaffold Python 3.14 boto3 FastAPI Amazon Bedrock DynamoDB CloudFormation

What it is

CloudGuard walks your AWS account service by service, collects security-relevant configuration facts, and turns each problem into a Finding - one typed record that flows through the whole system. Findings are scored deterministically, enriched with an AI explanation and recommended fix, stored in DynamoDB, and surfaced on a dashboard where a human approves or rejects each remediation.

Detect

Six scanners inspect IAM, S3, EC2, Security Groups, Lambda, and AWS Config for misconfigurations and non-compliance.

Reason

Bedrock explains the real-world risk, assigns a severity score, and recommends a concrete fix - with a deterministic fallback if the model is unavailable.

Act

High-severity findings fire SNS alerts. Approved findings are remediated by narrowly-scoped boto3 handlers - never automatically.

Architecture

A dashboard talks to a FastAPI Lambda through API Gateway. Scans run in a dedicated Lambda that drives the boto3 scanner engine; findings land in DynamoDB and branch out to alerts and optional remediation.

Module reference

The backend/ package is organized so each module owns one concern. Only database.py knows DynamoDB; only ai.py knows Bedrock; scanners never write anything.

models.py

The shared Finding dataclass with a deterministic FindingId, so re-scanning the same issue updates rather than duplicates the record.

config.py

Environment-driven configuration. Region defaults to ap-south-1. No AWS calls at import time.

scanner.py

The orchestrator: runs every scanner, scores, enriches with AI, persists, and alerts. Entry point for the Scan Lambda.

severity.py

Deterministic 0-100 baseline scores and the Critical/High/Medium/Low banding - works even without Bedrock.

ai.py

Bedrock enrichment via the model-agnostic Converse API. Never crashes a scan; falls back to the baseline score on failure.

remediation.py

Opt-in, per-check_id fix handlers. Refuses unknown checks and is disabled unless explicitly enabled.

database.py

DynamoDB access layer with float→Decimal handling and idempotent batch writes.

notifications.py

Publishes SNS alerts for findings at or above the severity threshold.

app.py

FastAPI app exposing scan/findings/approval endpoints, with a Mangum handler for Lambda + API Gateway.

scanners/

One module per service plus base.py and an auto-registry in __init__.py - add a class, the orchestrator picks it up.

Severity scoring

Every finding gets a deterministic baseline score from severity.py. The AI layer may override the number, but the baseline guarantees the system works - and stays testable - without Bedrock.

Bands

Critical   score ≥ 90

High   70 – 89

Medium   40 – 69

Low   < 40

Flow

scan_finding()
  → severity.score_finding()   # baseline
  → ai.analyze()               # may override
  → repo.save_many()           # persist
  → send_alert() if ≥ threshold

Setup & deploy

No AWS CLI. All AWS resources are provisioned from the console - either by deploying the CloudFormation template or through the service consoles directly.

  1. Deploy the core stack

    In the CloudFormation console, create a stack from infrastructure/cloudformation/cloudguard-core.yaml. It provisions the DynamoDB table, SNS topic + email subscription, and the Lambda execution role.

  2. Enable AWS Config & Bedrock

    Turn on AWS Config (record all resources) and request Bedrock model access in ap-south-1 from their consoles. These are click-throughs the code can't do for you.

  3. Configure the backend

    Copy backend/.env.example to .env and fill in the CloudFormation outputs (table name, topic ARN, model id).

  4. Run locally

    cd backend
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt
uvicorn app:app --reload

curl -X POST localhost:8000/scan

Infrastructure

Everything in infrastructure/ is deployable without a CLI and version-controlled with the code.

cloudformation/

cloudguard-core.yaml - DynamoDB (on-demand, encrypted, PITR), SNS topic + subscription, and CloudGuardLambdaRole with scoped writes.

policies/

cloudguard-scan-readonly.json - the least-privilege read policy to swap in for the broad managed ReadOnlyAccess.

lambda/

scan_handler.py - the Scan Lambda entrypoint that invokes the orchestrator.

IAM role permissions

  • AWSLambdaBasicExecutionRole + ReadOnlyAccess for scanning
  • Scoped DynamoDB writes on the findings table only
  • sns:Publish to the alerts topic only
  • bedrock:InvokeModel for AI analysis
  • Narrow S3 remediation actions (public-access block + encryption)

Remediation

Remediation never runs automatically. It is disabled unless CLOUDGUARD_REMEDIATION_ENABLED=true, and each fix runs only after a human approves that specific finding in the dashboard.

Handlers are keyed by check_id, so CloudGuard only ever applies a fix that has been explicitly written and reviewed. Unknown checks are refused rather than guessed at.
